# Use Scripture Burrito as the internal project model

Status: accepted, 17 September 2026

tC Admin models every project as Scripture Burrito: a `metadata.json` file and an `ingredients/` folder. It is the only format tC Admin writes. Every project tC Admin creates is Scripture Burrito, with tC Admin recorded as the generator.

Resource Container projects, which use `manifest.yaml`, are read through an RC-to-SB mapping inside the Worker that follows the same file naming as Door43's own Scripture Burrito archive. tC Admin never rewrites a Resource Container repository silently. A release from a Resource Container project keeps the repository's existing layout and updates only the manifest version and project entries. A manager-confirmed one-time conversion to Scripture Burrito is a later feature.

The pilot partner's active translation work is already Scripture Burrito, generated by Scribe, while their older repositories are Resource Container. One internal model with a read-through mapping means one form, one coverage rule, and one snapshot orchestrator, and it avoids asking managers to choose a format they do not care about. Scripture Burrito metadata has no version field, so the Door43 release tag is the only place a project version lives.

Supersedes the manifest-centric wording in the product specification, domain model, and architecture. ADR 0006 still applies: the protected project purpose is now the Scripture Burrito flavor rather than the Resource Container subject.
