# Use Scripture Burrito as the internal model and the release format

Status: accepted, 17 September 2026; amended 18 September 2026

tC Admin models every project as Scripture Burrito: a `metadata.json` file and an `ingredients/` folder. Every project tC Admin creates is Scripture Burrito, with tC Admin recorded as the generator. Every release tC Admin creates is Scripture Burrito, whatever format the repository's default branch uses.

Door43 already converts Resource Container, translationStudio, and translationCore repositories to Scripture Burrito on demand through its `/{owner}/{repo}/sb/{ref}.zip` archive, and serves a plain rollup for refs that are already Scripture Burrito. tC Admin uses that archive as its only way of reading a repository's content for release. It does not carry its own converter. The Worker downloads the archive for the default branch and, when a release exists, for the latest full release tag, and assembles the release from those two trees.

The default branch of a non-Scripture-Burrito repository is never rewritten by a release. The only writes a release makes are a temporary branch, one commit, a tag, and a Door43 release (see ADR 0010). A manager-confirmed conversion of the default branch itself is a separate later feature.

The pilot partner's active translation work is Scripture Burrito generated by Scribe, their older repositories are Resource Container, and other partners still release translationStudio and translationCore repositories. One release format with Door43 doing the conversion means one snapshot orchestrator, one health-check shape, and no divergence from what Door43 itself would produce. Scripture Burrito metadata has no version field, so the Door43 release tag is the only place a project version lives.

Supersedes the manifest-centric wording in the product specification, domain model, and architecture. ADR 0006 still applies: the protected project purpose is the Scripture Burrito flavor.
